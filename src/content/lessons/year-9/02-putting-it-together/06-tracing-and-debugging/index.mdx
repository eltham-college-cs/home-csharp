## The big idea

A **trace table** lets you be the computer. You go one line at a time and write down what is in every box.

The trickiest line is one like this:

```csharp
score = score + 5;
```

Read it from the **right**: take what is in `score`, add 5, then put the answer back in the `score` box. The old value is thrown away.

Notice there is no `int` at the start. `int score = 8;` **creates** the box, once. After that you just use its name.

## Swap two values

To swap two boxes you need a spare box called `temp`. Without it, the first value is overwritten and lost.
Assume the user types red, then blue.

## Two kinds of error

C# can go wrong in two different ways.

- A **compile error** (also called a build error) is found **before** the program runs. C# reads your whole program first, and if anything doesn't make sense, **none** of it runs. Missing semicolons, misspelt names and putting text in an `int` box are all compile errors.
- A **runtime error** happens **while** the program is running. Everything before it has already happened, then the program stops. For example, `int.Parse()` can't turn the word seven into a number, so the program stops with a `FormatException`.

Every compile error has a **line number** and a code that starts with **CS**. The checker shows it like this:

```
Your code didn't build. The first problem is on line 3:
CS0103: The name 'Bonus' does not exist in the current context
```

Read it like this: look at **line 3**. The code **CS0103** means "C# doesn't know that name". The message tells you which name: `Bonus`.

The messages can be hard to read. The **Error decoder** page (in the menu at the top) explains each one in plain English, with a broken and a fixed example. When the checker shows an error, it gives you a link straight to the right entry.

<Note title="Fix the first error first">
One slip can confuse C# about the lines after it. The checker shows only the first error. Fix that one, run again, and the others often disappear.
</Note>
